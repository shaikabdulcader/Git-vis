🧠 What is Git?

Git is a Version Control System — a magical "save game" button for an entire project that also remembers every save you ever made.

🧪 Tester Analogy

Imagine naming your test case files: TestCase_v1.docx, TestCase_v2.docx, TestCase_v3_FINAL.docx, TestCase_v3_FINAL_really.docx…

Painful. 😅

Git does all of that automatically. Every version saved, every change tracked, every author known — and you can time-travel to any point.

Why developers & testers love Git

⏮️

Time Travel

Go back to any version of your project from any point in history.

👥

Teamwork

Many people work on the same project at the same time — safely.

🧪

Experiment Safely

Try risky changes in a separate "branch" without breaking main.

📝

Full History

Who changed what, when, and why — perfect for audits and bug tracing.

Key terms you'll hear a lot

TermSimple meaning
RepositoryA project folder tracked by Git. Also called "repo".
CommitA saved snapshot at a specific moment.
BranchA separate line of work. Like a safe copy you can edit.
CloneDownloading a repo to your computer.
PushUploading your changes to the shared online repo.
PullDownloading the latest changes from the shared online repo.

🐙 What is GitHub?

If Git is the tool, GitHub is the place where projects live online — and where teams collaborate.

Easy way to remember

🎮 Git = The app on your laptop that saves your game progress.
☁️ GitHub = The cloud server that stores your saves and lets friends join.

Git vs GitHub

GitGitHub
A software/toolA website / cloud platform
Runs on your computerRuns on the internet
Tracks file changesHosts Git repositories online
Works offlineNeeds internet
Free & open sourceOwned by Microsoft

🧪 Your role as a tester in a PR

1. Read the description — understand what changed.
2. Check out the branch locally and test it.

4. Comment with your findings — pass, fail, bugs.

Two testers each wrote test cases. Merge combines both into one master doc — keeping everyone's work intact. A "merge commit" ties them together.

✅ Pros & ❌ Cons of Merge

✅ Keeps the full real history    ✅ Safe — no history is rewritten
❌ Can create a messy log with lots of "merge commits"

Merge vs Rebase

MergeRebase
Preserves exact historyRewrites history for cleanliness
Creates a "merge commit"No extra merge commit
History looks like a tree 🌳History looks like a straight line 📏
Safe for shared branchesRisky on shared branches

⚠️ Golden rule of rebase

Only rebase your OWN private branch. Never rebase a branch others are working on.

🧪 Tester Analogy

You file 6 small bug reports: "typo", "typo v2", "oops", "fix again", "re-fix", "done". Noisy, right? Squash combines all 6 into one: "Fix login page typos". Same result, way easier to read.

💡 When to use Squash

Before opening a PR — tidy your messy WIP commits so reviewers see one clear change instead of 20 noisy ones.

🎭 Playwright + Git — Real Workflow

Let's write a real Playwright test for Wikipedia, then walk through every git command to push it as a Pull Request. Click Next Step to progress.

Step 0 — The test we're going to add

We'll write a simple Playwright test that opens Wikipedia, searches for "Playwright", and verifies the result page loads correctly.

// tests/wikipedia-search.spec.js import { test, expect } from '@playwright/test'; test('Wikipedia search for Playwright returns correct page', async ({ page }) => { // 1. Open Wikipedia await page.goto('https://www.wikipedia.org'); // 2. Type into the search box await page.fill('#searchInput', 'Playwright'); // 3. Click the search button await page.click('button[type="submit"]'); // 4. Verify the URL changed to the Playwright article await expect(page).toHaveURL(/Playwright/); // 5. Verify the main heading contains "Playwright" await expect(page.locator('h1')).toContainText('Playwright'); }); test('Wikipedia language link works', async ({ page }) => { await page.goto('https://www.wikipedia.org'); await page.click('text=English'); await expect(page).toHaveURL(/en.wikipedia.org/); });

Now — ship it with Git

Step 0 / 7
1

🌿 Create a test branch

Start a new branch so you don't touch main while writing your test.

$ git checkout -b test/wikipedia-search Switched to a new branch 'test/wikipedia-search'
2

📝 Write the test file

Create the file tests/wikipedia-search.spec.js with your Playwright code (shown above).

3

🔍 Check what git sees

Verify git has noticed your new file.

$ git status On branch test/wikipedia-search Untracked files: tests/wikipedia-search.spec.js
4

➕ Stage & commit the test

Add the file to staging and commit it with a clear message.

$ git add tests/wikipedia-search.spec.js $ git commit -m "Add Playwright test for Wikipedia search" [test/wikipedia-search 7a2b4c9] Add Playwright test for Wikipedia search 1 file changed, 18 insertions(+)
5

📡 Fetch latest from the remote

Grab any new work your teammates pushed — without changing your branch.

$ git fetch origin remote: Enumerating objects: 12, done. From github.com:qa-team/web-tests * [new branch] bugfix/signup -> origin/bugfix/signup ✓ Remote info updated
6

☁️ Push with upstream tracking

First push of a new branch? Use -u so git remembers the link for future pulls/pushes.

$ git push -u origin test/wikipedia-search Enumerating objects: 5, done. To github.com:qa-team/web-tests.git * [new branch] test/wikipedia-search -> test/wikipedia-search Branch 'test/wikipedia-search' set up to track 'origin/test/wikipedia-search'
7

📬 Open the Pull Request on GitHub

Go to the GitHub repo page. A yellow banner says "Compare & pull request" — click it, add a description, and submit. Your test is now ready for review.

✓ PR #87 opened: "Add Playwright test for Wikipedia search" Reviewers: @ajinroch, @karan Status: ✅ CI tests passed · Awaiting review

🧪 Why this matters for you

This is exactly how a QA engineer ships automation code. Every test case you write — Playwright, Selenium, Cypress — follows this same flow: branch → write → stage → commit → fetch → push with -u → open PR. Memorize this sequence.

What happens after you push?

🤖

CI runs your test

GitHub Actions (or Jenkins) automatically runs npx playwright test and shows a green ✅ or red ❌.

👥

Team reviews

Senior QA or dev reviews your test code — checks selectors, assertions, naming.

💬

You address feedback

Make changes locally → git commit → git push (no -u needed now).

✅

Merge & celebrate

Approved! Click "Squash and merge" — your test is now part of the main suite.

Everyday workflow

CommandWhat it does
git statusSee what changed, what's staged
git add <file>Stage a specific file
git add .Stage everything changed
git commit -m "message"Save a snapshot with a message
git fetch originDownload remote updates (no auto-apply)
git pullFetch + merge the latest changes
git pushUpload commits to the already-linked branch
git push -u origin <branch>First push of a new branch — sets upstream
git diffShow unstaged changes

Branching

CommandWhat it does
git branchList all branches
git branch <name>Create a new branch
git checkout <name>Switch to a branch
git checkout -b <name>Create & switch in one command
git branch -d <name>Delete a branch

Merge / Rebase / Squash

CommandWhat it does
git merge <branch>Combine another branch into current one
git rebase <branch>Replay your commits on top of another branch
git rebase -i HEAD~NInteractive rebase — squash last N commits

Undoing things (lifesavers!)

CommandWhat it does
